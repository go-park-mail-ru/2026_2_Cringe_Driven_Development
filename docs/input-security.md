# Защита пользовательских данных

Документ описывает защиту данных от SQL-инъекций и XSS, серверную проверку BFF по [backend#41](https://github.com/Cringe-Driven-Development-Team/backend/issues/41) и исторические результаты проверки [backend#20](https://github.com/Cringe-Driven-Development-Team/backend/issues/20).

## SQL: данные передаются параметрами

Все запросы прикладных репозиториев используют `$1`, `$2` и отдельные аргументы pgx:

- `internal/user/adapters/postgres/user.go`: создание и чтение пользователей, создание и удаление refresh-сессий;
- `internal/notebook/adapters/postgres/notebook.go`: создание, список, чтение и изменение метаданных блокнотов.

Конкатенация `selectNotebook + " FOR UPDATE"` объединяет константы. Пользовательские значения не участвуют в построении SQL. Чтение блокнота и блокировка строки перед изменением ограничены одновременно `id` и `owner_id`; список ограничен владельцем. Чужой блокнот возвращает `404`.

Логин ограничен контрактом `^[a-zA-Z0-9_]+$`, но валидация не заменяет параметризацию. Имя блокнота может содержать кавычки, SQL-подобные фрагменты и HTML-подобный текст. Например, `x'); DROP TABLE notebooks; --` должно сохраняться обычным именем.

Новые запросы должны передавать значения через аргументы драйвера. Если появятся пользовательские сортировки или SQL-идентификаторы, для них нужен фиксированный список разрешённых вариантов: placeholder предназначен для значений.

## XSS: текст хранится исходным, выводится безопасно

Текущий API возвращает JSON, а не HTML. Имя блокнота и `cell.source` сохраняются без `html.EscapeString`, удаления тегов или декодирования HTML-entities. Уже введённое `&lt;script&gt;` остаётся именно такой строкой. Пароли и токены также нельзя изменять HTML-преобразованиями.

`encoding/json` может записывать `<` как `\u003c`: это представление JSON, после декодирования получается исходный символ. Оно не заменяет защиту в месте отображения.

В текущем клиенте:

- `NotebookCard` и `NotebookPage` выводят имя через JSX; `title` задаётся свойством DOM;
- `Cell` показывает обе разновидности ячеек, `code` и `markdown`, текстом внутри `<pre>`;
- текст серверной ошибки отображается текстовым содержимым компонента формы.

В проверенной `@cdd-team/react@1.2.1` текстовые узлы создаются через `document.createTextNode`, обновляются через `nodeValue`; свойства и атрибуты задаются DOM API. Обработчики событий устанавливаются через `addEventListener` только для функций. Пользовательский текст в проверенных компонентах не передаётся в `innerHTML`.

Экранирование до безопасной вставки в DOM привело бы к двойному экранированию и порче кода, например `if a < b:`. Если появятся серверные HTML-шаблоны, использовать контекстное экранирование `html/template`. Если появится рендеринг Markdown или `text/html` из результатов исполнения, перед вставкой итогового HTML нужна отдельная политика санации тегов, атрибутов и URL-схем. Не считать текущую проверку текстового `<pre>` проверкой будущего HTML-рендерера.

## BFF: проверка сервиса до бизнес-операций

`internal/transport/http/security.S2S` проверяет единственный `X-BFF-Key` на всех
запросах к `/api/v1` до Bearer, разбора параметров и тела. Отсутствующий, неверный
или повторяющийся ключ даёт `403 s2s_forbidden` без обращений к пользовательским
сессиям, метаданным блокнотов и S3. `GET /health` исключён из проверки.

Go получает access через `Authorization: Bearer`, refresh — в JSON-теле auth-запросов.
Браузерные cookie, CSRF и CORS в Go API отсутствуют. Браузер обращается к BFF;
за его браузерную политику отвечает frontend. Общий S2S-ключ передаётся только между
серверами. Подробный контракт: [авторизация](authentication.md).

## Автоматические проверки

Из корня backend:

```sh
go test ./internal/user/adapters/postgres ./internal/notebook/adapters/postgres -run Parameterized -count=1
go test ./internal/notebook/delivery/http ./internal/notebook/usecase ./internal/notebook/adapters/ipynb ./internal/user/delivery/http -count=1
go test ./internal/transport/http ./internal/transport/http/security ./internal/transport/http/middleware -count=1
make check
make docker-build
```

SQL-тесты используют pgxmock/v5 с точным сравнением SQL (`QueryMatcherEqual`), аргументов (`WithArgs`) и обязательной проверкой всех ожиданий. Они проверяют запросы, которые репозитории передают драйверу: пользовательская строка находится в аргументах, а не в SQL; присутствуют placeholders, условие владельца и блокировка строки для изменения. Это проверки границы приложения с драйвером, а не замена запуска с PostgreSQL.

Тесты текста проверяют JSON-ответы, вход хендлеров, сохранённое имя и два последовательных цикла сборки/разбора `.ipynb`. В наборе есть `<script>`, `<img onerror>`, кавычки, `&`, буквальное `&lt;`, кириллица и код со сравнением `<`. Невалидный логин не доходит до usecase, пароль со специальными символами передаётся без изменений.

`TestS2SRejectionDoesNotTouchNotebookStorage` использует настоящий notebook usecase и codec со сгенерированными gomock-портами PostgreSQL/S3: отказ S2S не читает и не пишет файлы, не изменяет метаданные и сессии. Положительный контроль с валидным токеном проходит через те же порты. Проверки отсутствия изменений сессии и порядка S2S перед Bearer есть в `TestBFFRouterS2SPriorityAndRequestID` и `TestMandatoryS2SBeforeBearer`.

## Проверка с PostgreSQL и браузером

Проводить на отдельном локальном окружении с тестовыми пользователями и хранилищем. Не подменять файлы рабочего окружения ради проверки XSS.

1. Серверные запросы к Go передают корректный `X-BFF-Key`, а защищённые операции — Bearer. Браузерные запросы идут через BFF. Зарегистрировать двух пользователей. От первого создать блокноты с именами из таблицы ниже; проверить ответ создания, список, открытие и точное имя в PostgreSQL. Таблицы пользователей и блокнотов должны остаться доступны.
2. От второго проверить пустой список и `404` при чтении чужого ID. SQL-подобный логин должен получить `400 validation_error` без новой сессии.
3. С доверенного сервера отправить создание с Bearer первого пользователя, но без `X-BFF-Key`, затем с неверным ключом. Ожидается `403 s2s_forbidden`; количество строк блокнотов в БД не меняется. Не передавать общий ключ браузеру.
4. В браузере открыть список и страницы созданных блокнотов. Проверить `textContent`, `title` и DOM: нет созданных из текста `script`, `img` и атрибута `onmouseover`, нет выполнения `alert`. Повторить после перезагрузки.
5. Для проверки `source` подложить контролируемый `.ipynb` в локальный S3 по `file_key` тестового блокнота либо подменить ответ чтения только в браузере. Создание ячейки сейчас не принимает произвольный `source`. В файле поместить строки из таблицы в ячейки `code` и `markdown`; проверить JSON, затем текст и отсутствие вложенных HTML-элементов в `<pre>`, включая повторное открытие.
6. Подменить ответ входа только в браузере на `400` с `code: validation_error` и `message: "<img src=x onerror=alert(1)>"`. Отправить форму и убедиться, что сообщение видно текстом, без созданного изображения и исполнения обработчика.

### Зафиксированный результат: 24 октября 2026 года

Это историческая проверка до перехода на BFF. Результат CSRF ниже относится к прежнему API; он не подтверждает проверку S2S или работу через BFF.

Backend: базовая ревизия `4d8d5dd` и изменения ветки `api-20` с этими тестами; прикладная реализация не изменялась. Frontend: `75e0ac7`, исходники скопированы в временный каталог, рабочий репозиторий frontend не изменялся. Проверялась `@cdd-team/react@1.2.1`, как в `bun.lock`; также зафиксированы версии `@cdd-team/zustand@1.0.1` и `@cdd-team/openapi@0.2.1`. Окружение проверки: Vite 8.3.5, Chromium 156.0.8078.4 через Playwright 1.61.1, PostgreSQL из `postgres:18-alpine`, SeaweedFS 4.48, локально собранный API.

| Ввод / сценарий | Где проверено | Результат |
|---|---|---|
| `<script>alert(1)</script>` | Имя карточки/страницы, `title`, обе разновидности ячеек | Исходный текст, выполнение отсутствует |
| `<img src=x onerror=alert(1)>` | Имя, ячейки, сообщение ошибки формы | Изображение не создаётся, обработчик не выполняется |

Проверены 7 имён и 16 ячеек, отражённая ошибка формы. Для списка, всех семи страниц блокнотов и всех 16 ячеек проверки точного текста и DOM повторены после перезагрузки; для имён также проверены `title` и отсутствие нового `onmouseover`. Общий для навигаций счётчик выполнения XSS — 0, необработанных ошибок JavaScript — 0. Проверка `source` использовала настоящий файл в отдельном тестовом S3. Полноценный ввод и сохранение `source` через редактор этим не подтверждаются: такого сценария в текущем API нет.

Результат относится к указанным ревизиям и текущему текстовому отображению. Повторить браузерную проверку при изменении DOM-библиотеки, способов вставки строк или появлении HTML/Markdown-рендеринга.

## Границы

Эта защита не выполняет антивирусное сканирование произвольных загрузок и не изолирует исполняемый Python. HTML, SVG и интерактивные результаты runtime требуют собственного решения до их отображения. Эти проверки не означают защиту от любого вредоносного файла.
