# Профиль пользователя

Все операции требуют `X-BFF-Key` и `Authorization: Bearer <access_token>`.
Пользователь определяется по проверенной сессии; передать чужой ID нельзя.
Данные профиля приходят также в register/login: `id`, `login`, `avatar_url`.
До первой загрузки аватара `avatar_url` равен `null`.

| Операция | Запрос | Успех |
| --- | --- | --- |
| `GET /api/v1/users/me` | Без тела | `200 User` |
| `PATCH /api/v1/users/me` | JSON `{"login":"new_login"}` | `200 User` |
| `PUT /api/v1/users/me/password` | JSON `{"current_password":"old_password","new_password":"new_password"}` | `204` без тела |
| `PUT /api/v1/users/me/avatar` | `multipart/form-data`, один файл `avatar` | `200 User` |

Логин — 3–32 символа из `a-z`, `A-Z`, `0-9`, `_`. Занятый логин возвращает
`409 login_taken`, неверный формат — `400 validation_error`. Несуществующий
пользователь действующей сессии получает 401.

## Смена пароля и сессии

Текущий пароль проверяется по хешу PostgreSQL; неверный пароль даёт
`400 invalid_current_password`. Новый пароль должен отличаться от текущего,
содержать 8–72 символа и занимать не больше 72 байт UTF-8; нарушение —
`400 validation_error`. Пустые поля и невалидный UTF-8 отклоняются.
Пароли не обрезаются и не нормализуются.

Смена хеша выполняется условно по прежнему хешу; затем Redis отзывает все сессии,
включая текущую. После `204` старые access/refresh больше не принимаются,
клиенту нужен новый login. Сбой PostgreSQL или Redis возвращает `500 internal`;
API не подтверждает успешный отзыв и не повторяет мутацию с неизвестным исходом.
При таком ответе пароль уже мог измениться. Обычный logout, logout-all и
границы отзыва описаны в [авторизации](authentication.md).

## Загрузка аватара

Поддерживаются JPEG и PNG. MIME файла должен соответствовать его сигнатуре.
Ширина и высота независимо находятся в диапазоне 200–4096 пикселей включительно.
Размер файла — не больше 5 МиБ; весь multipart-запрос — не больше 6 МиБ.
Допускается ровно одна часть: файл `avatar` с непустым именем. Дополнительные
файлы и текстовые поля отклоняются.

До полного декодирования API проверяет размеры через DecodeConfig.
Изображение сохраняется в исходном формате и размере: JPEG с качеством 85,
PNG с прозрачностью, сведённой на белый фон. Повторное кодирование удаляет
метаданные. Исходный файл и очищенный результат проходят через временные файлы
с правами `0600` в системном каталоге temp и удаляются при завершении запроса.
Закодированные файлы не накапливаются целиком в памяти; растровое представление
ограничено проверенными размерами. Один слот на процесс ограничивает весь путь
от чтения multipart до сохранения, остальные запросы ожидают с учётом отмены.

Новый объект получает случайный ключ `avatars/<uuid>.jpg` или `.png` в отдельном
бакете. Сначала завершается запись S3, затем меняется ссылка в PostgreSQL.
Прежний объект удаляется после успешной замены; сбой удаления не отменяет новый
аватар. Если исход записи PostgreSQL неизвестен, новый объект сохраняется,
чтобы не удалить файл, на который уже мог ссылаться профиль. Объекты-сироты
возможны; автоматическая фоновая уборка не реализована.

| Ответ | Причина |
| --- | --- |
| `400 validation_error` | Пустой/повреждённый файл, неверные размеры или структура multipart |
| `413 payload_too_large` | Превышен лимит файла или всего HTTP-тела |
| `415 unsupported_media_type` | Неверный тип запроса/файла или MIME не совпадает с форматом |
| `401 unauthorized` | Нет действующей сессии или пользователь удалён |
| `403 s2s_forbidden` | Неверный ключ BFF |
| `500 internal` | Сбой БД, S3 или временного файлового хранилища |

Для запуска обязательны `S3_AVATARS_BUCKET` и `S3_AVATARS_PUBLIC_URL`.
URL профиля строится как `<S3_AVATARS_PUBLIC_URL>/<object-key>`; публичный
адрес должен вести именно к бакету аватаров. Запись и удаление S3 используют
таймаут 5 секунд и одну попытку. Локальная настройка — в
[локальной разработке](local-development.md#s3-и-аватары); production бакет,
публичное чтение и CDN принадлежат infra (infra#30).
