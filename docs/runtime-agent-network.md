# Сеть runtime-agent: контракт backend и infra

Агент обслуживает одну сессию на выделенной VPS. Backend запускает контейнер в
подготовленной сети, но не создаёт сеть, NAT, firewall или VPS. Политику ниже
реализует роль `runtime_host` в infra ([infra#89](https://github.com/Cringe-Driven-Development-Team/infra/issues/89)),
а применяет backend-воркер при создании каждой VPS
([runtime-provisioning.md](runtime-provisioning.md)); сама политика не меняется. Имя сети
передаётся через KERNEL_NETWORK, IPv4 DNS — через KERNEL_DNS. Запуск отклоняет
неизвестную сеть, host/default bridge, IPv6 и internal-сеть без выхода в интернет.

## Обязательная политика infra

Перед запуском агента infra создаёт отдельную Docker bridge-сеть и устанавливает
правила для её интерфейса/подсети. Для VPS без public IP настраивается облачный NAT.
Правила не должны менять доступ Go API/БД и SSH управления.

| Направление | Политика |
| --- | --- |
| Контейнер → публичный интернет | TCP 80/443 |
| DNS | TCP/UDP 53 только к KERNEL_DNS |
| Ответы на разрешённые запросы | ESTABLISHED, RELATED |
| Контейнер → хост, включая агент и gateway bridge | Запрет новых соединений |
| Контейнер → backend, другие VPS, служебные и внутренние адреса | Запрет |
| Хост агента → Jupyter контейнера | TCP 8888, единственное служебное исключение |
| Любые другие новые входящие → контейнер | Запрет, включая соседей той же bridge-сети |
| Остальное | Запрет |

Запрет назначений имеет приоритет над разрешением TCP 80/443: приватные сети,
loopback внешнего хоста, link-local/metadata, multicast, зарезервированные
диапазоны и публичные IP инфраструктуры должны быть закрыты. Loopback внутри
самого контейнера нужен Jupyter/kernel и остаётся рабочим. Если выбранный DNS
находится в служебной сети, исключение касается только его TCP/UDP 53.

IPv6 отключён и в сети, и sysctl контейнера. Обход запретов через альтернативный
DNS, прямой IP, IPv6 или DNS rebinding не должен открывать доступ: фильтруется
фактический IP назначения, а не только hostname. Docker embedded DNS должен
пересылать запросы только выбранному резолверу; маршруты через хост и Docker DNS
не должны открывать произвольный исходящий трафик хоста по запросу контейнера.

Для iptables backend Docker нужны правила FORWARD/DOCKER-USER и отдельная
защита INPUT хоста; одного DOCKER-USER недостаточно для контейнер → сам хост.
Для nftables infra использует подходящие собственные цепочки и приоритеты.
UFW и отсутствие опубликованных портов сами по себе политикой не являются.
Правила устанавливаются до старта агента и восстанавливаются после reboot и
рестарта Docker; сбой их установки не должен разрешать запуск пользовательского kernel.
Агент проверяет форму сети, но не может доказать наличие корректного firewall.

## Приёмка на одноразовой Linux VPS

Эти действия выполняются на отдельном тестовом стенде с политикой infra.
Не устанавливайте экспериментальные правила firewall на общей рабочей машине.

1. Подготовить образы через `make agent-images`, bridge и firewall средствами infra.
2. Поднять контролируемые TCP-listeners для пяти направлений: host, backend,
   other_vps, metadata и public_infra. Для metadata использовать тестовый адрес/
   namespace, имитирующий служебное назначение; не считывать настоящие credentials.
   Для каждого listener подтвердить доступ с хоста агента — закрытый порт не
   считается доказательством сетевой изоляции. Адреса listeners — IPv4.
3. Задать KERNEL_NETWORK, KERNEL_DNS и NETWORK_BLOCKED_ENDPOINTS, например:

   ```bash
   export KERNEL_NETWORK=cellestial-kernel
   export KERNEL_DNS=1.1.1.1
   # Реальные адреса и порты живых listeners вашего одноразового стенда:
   export NETWORK_BLOCKED_ENDPOINTS='{"host":{"ip":"172.30.0.1","port":18080},"backend":{"ip":"10.0.0.2","port":18080},"other_vps":{"ip":"10.0.0.3","port":18080},"metadata":{"ip":"169.254.169.254","port":18080},"public_infra":{"ip":"203.0.113.10","port":18080}}'
   make agent-network-check
   ```

   Пример адресов нельзя запускать без соответствующих listeners. Проверка сначала
   подтверждает доступность endpoints с хоста, затем проверяет запрет из kernel,
   DNS, установку Python-пакета через HTTPS, отключение IPv6 и запрет соединений
   от соседнего контейнера. Jupyter доступен агенту, host-порт не публикуется.
4. Сохранить журнал результатов для kernel Python.
5. С другой VPS проверить недоступность container IP:8888 и IP:9999, а также
   отсутствие опубликованных портов на public/private IP хоста. Сопоставить отказ
   со счётчиками firewall. Проверить произвольный TCP-порт, отличный от 80/443,
   и DNS к другому контролируемому резолверу; они должны блокироваться.
6. Повторить приёмку после рестарта Docker и reboot VPS. При ошибке firewall
   пользовательский сервис запускаться не должен.

Обычный CI `agent-integration` проверяет протокол и ограничения контейнера во
временной сети без production firewall. Он не закрывает сетевую приёмку.

## Черновик задачи infra

Заголовок: `DevOps. Подготовить изолированную сеть VPS для runtime-agent`.

### Цель

Разрешить установку Python-пакетов из интернета на выделенной VPS сессии,
запретив доступ kernel к хосту и инфраструктуре.

### Что сделать

- Подготовить IPv4 bridge, DNS и исходящий NAT согласно таблице выше.
- Установить firewall до запуска агента, включая INPUT хоста и peers bridge.
- Настроить порядок systemd и восстановление правил после Docker/reboot.
- Передавать агенту KERNEL_NETWORK и KERNEL_DNS; сессию, язык и токен назначает Go API
  запросом `POST /assign` (backend#89). Не переиспользовать прежний STATE_DIR.
- Доставить шаблоны сервиса и образы без включения production-конфигурации в backend.

### Приёмка

Пройти сценарий выше, сохранить результаты Python, отрицательных сетевых
проверок и повторов после reboot. Ошибка подготовки сети блокирует старт агента.

### Зависимости

Backend API-16 / PR #45 поставляет контракт, агент и проверочный сценарий.
Production-включение доступа в интернет возможно только после приёмки infra.
Управление и пополнение пула VPS — отдельная задача.

### Не входит

Go-интеграция, пользовательские квоты, сохранение ipynb и выдача машин из пула.
