# Перенос существующих ipynb в PostgreSQL

Перенос запускается при остановленном API и всех источниках изменения блокнотов
(включая runtime-запись результатов). Сначала сохранить проверенные резервные
копии PostgreSQL и доступ к исходным S3-объектам. Старый API после изменения схемы
запускать нельзя. Безостановочное переключение и двойное чтение не предусмотрены.

SQL-миграция создаёт таблицы ячеек и переносит актуальные соответствия `file_key`
в `notebook_legacy_sources`, удаляя колонку из `notebooks`. Эта временная таблица
принадлежит только инструменту переноса. Обычный API отказывается запускаться,
если есть неперенесённые или неподтверждённые блокноты.

## Запуск

Собрать инструмент из корня backend:

```bash
go build -o bin/notebook-migrate ./cmd/notebook-migrate
```

Передать в окружении `NOTEBOOK_MIGRATION_DATABASE_URL`,
`MIGRATION_S3_NOTEBOOKS_BUCKET` и стандартные `AWS_*` для чтения старого бакета.
Пароли и ключи не вставлять в команды и не сохранять в отчётах. Инструменту не
требуются JWT, Redis или настройки аватаров. Затем:

```bash
bin/notebook-migrate
bin/notebook-migrate -verify
```

Первый запуск сам применяет встроенные SQL-миграции. Для каждого документа он
читает актуальный объект, нормализует source и JSON, проверяет ограничения,
сохраняет ячейки и все поля, читает их обратно и сверяет компактный экспорт
**до коммита**. ID блокнота, владелец, cell ID, порядок и даты сохраняются.
Редакция становится новым непрозрачным токеном; клиенты должны перечитать content.

Ошибка одного документа откатывает его целиком; остальные продолжают переноситься.
Итог содержит migrated/verified/skipped/failed, ненулевой код означает ошибку.
После устранения причины повторить ту же команду: подтверждённые блокноты
пропускаются без изменения редакций и дублей. Ошибки исправляются по исходным
данным явно, а не молчаливым удалением неизвестных полей или недопустимых символов.

`-verify` не применяет миграции и не пишет данные: повторно сравнивает каждый
документ с S3, нормализуя только допустимые представления JSON/source, и проверяет
равенство длины экспорта `size_bytes`. Запускать до возобновления записей, иначе
новые правки закономерно дадут несовпадение с архивным объектом.

## Завершение

После нулевого кода обеих команд проверить количество документов и ячеек,
выборочно открыть content и список с превью. Затем запустить новый API без
`S3_NOTEBOOKS_BUCKET`. Проверить создание, редактирование, повторное открытие
с результатами и загрузку/отображение аватара.

Исходные объекты и бакет автоматически не удаляются. Таблица соответствий остаётся
для аудита и повторной offline-сверки; рабочие операции блокнотов её не читают.
Удаление архивов и таблицы выполняется отдельным решением после приёмки.
Миграция Down намеренно запрещена: восстановление старого приложения требует
восстановления резервной копии БД, без удаления исходных S3-объектов.

Production env принадлежит infra. В `ansible/roles/app/templates/env.j2` убрать
передачу `S3_NOTEBOOKS_BUCKET`, в `tasks/validate.yml` — обязательность
`notebooks_bucket`; сохранить общий AWS-доступ и настройки аватаров. Связь изменения:
`Part of Cringe-Driven-Development-Team/backend#65`. Эти правки и выкатка здесь
автоматически не выполняются.

## Проверка производительности

На отдельной тестовой БД PostgreSQL 18:

```bash
TEST_POSTGRES_DSN='<адрес тестовой БД>' NOTEBOOK_LARGE_TEST=1 \
  go test -v -count=1 -timeout=8m ./internal/notebook/adapters/postgres \
  -run TestLargeNotebookAccountingAndAutosave
```

Тест создаёт документ ровно 128 МиБ с несжимаемыми outputs/attachments, проверяет
откат превышения для source и результата, затем сохраняет короткий source раз
в секунду в течение минуты с актуальным токеном. Повторяет сценарий без тяжёлых
данных. Выводит p50/p95, RSS, WAL и подтверждает неизменность xmin/ctid тяжёлых
строк. Не запускать на production. Результаты текущего стенда — в отчёте приёмки.
