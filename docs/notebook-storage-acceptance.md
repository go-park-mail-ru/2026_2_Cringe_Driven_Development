# Проверка хранения блокнотов по ячейкам

Дата: 2026-11-05. Локальная проверка рабочей ветки `api-65`, без выкладки.

## Стенд

Linux WSL2 `6.18.54.1-microsoft-standard-WSL2`, amd64, 32 доступных CPU,
около 16 ГиБ RAM, файловая система ext4. Go 1.27.1. PostgreSQL 18.0 собран
GCC 13.3.0 и запущен локально; `shared_buffers=128MB`, `max_connections=100`,
`fsync=on`, `synchronous_commit=on`, `full_page_writes=on`, `wal_compression=off`.
В начале сессии Docker был недоступен; к финальным проверкам daemon стал доступен,
`make docker-build` успешно собрал `colab-backend:local`.

## Размер и минутный autosave

`TestLargeNotebookAccountingAndAutosave`: экспорт ровно **134217728 байт**,
включая несжимаемые base64 outputs и attachments в других ячейках. Физический
размер этих JSONB-значений — 134217387 байт. Это полный документ, а не маленькая
или хорошо сжимаемая имитация. У второго блокнота без тяжёлых данных — 338 байт.

Оба прогона: 60 последовательных изменений source по три ASCII-символа,
одно в секунду в течение минуты, каждый раз с актуальной редакцией. Перед
измерением освобождена память полной сборки/импорта. Процентили — nearest rank.

| Сценарий | p50 | p95 | RSS до / максимум | WAL |
| --- | ---: | ---: | ---: | ---: |
| 128 МиБ | 4,963 мс | 50,535 мс | 17260544 / 17653760 байт | 1236800 байт |
| Без тяжёлых данных | 4,890 мс | 7,286 мс | 17342464 / 17711104 байт | 82568 байт |

Это измерения локального стенда с обычными настройками WAL и полной записью
страниц, не гарантия задержки production. WAL измерен через разность
`pg_current_wal_insert_lsn()` до/после каждого прогона. Тяжёлые строки сохранили
`xmin` и `ctid` за все 60 изменений: outputs `(0,2)`, attachments `(0,3)`.

SQL-трасса измеряемых сохранений содержит 960 команд для 120 операций,
восемь на операцию:

1. BEGIN.
2. Выбор компактных полей блокнота `FOR UPDATE`.
3. Выбор целевой ячейки: ID, kind, source, source_version, position и числовые
   размеры частей. JSONB outputs/attachments/metadata не выбираются.
4. UPDATE source, версии source, размера лёгкой части и флага кандидата превью.
5. Сброс результатов только изменяемой code-ячейки.
6. Выбор source первого кандидата превью, `LIMIT 1`.
7. UPDATE редакции, количества ячеек, превью, размера и даты блокнота.
8. COMMIT.

В измеряемом пути нет полной сборки, разбора ipynb, SHA-256 или S3.
Неизменённые тяжёлые строки не обновляются. Превышение предела изменением source
на один байт и записью runtime-результата возвращает ErrTooLarge и сохраняет
прежние данные и редакцию.

Повтор:

```bash
TEST_POSTGRES_DSN='<тестовая БД>' NOTEBOOK_LARGE_TEST=1 \
  NOTEBOOK_SQL_TRACE=/tmp/autosave-sql.log \
  go test -v -count=1 -timeout=8m ./internal/notebook/adapters/postgres \
  -run TestLargeNotebookAccountingAndAutosave
```

Трасса сохраняет только SQL, без значений параметров.

## Функциональная приёмка

PostgreSQL-тесты проверяют транзакционные правки, перемещения, no-op, конкуренцию
с одинаковой редакцией, снимок с коммитом между чтением метаданных и ячеек,
откат при ошибке публикации, сохранение полей при переносе и повторный перенос.
Проверены source ABA, отказ для удалённой ячейки, сохранение результата после
перемещения и правок соседей, сброс только собственных результатов и сохранность
attachments. Контрактные тесты проверяют outputs/count/truncation при открытии.
Активная сессия проверяется через тестовую реализацию порта #13, включая успешный
и ошибочный результат исполнения и последующее завершение сессии.

## Проверка запуска и аватаров

В отдельном Compose-проекте `api65-verification` с тестовыми credentials и портами
18065/15465/18365 подняты API, PostgreSQL 18, Redis 8 и SeaweedFS. Проверка
container environment подтвердила отсутствие `S3_NOTEBOOKS_BUCKET`. Через HTTP
успешны регистрация, создание блокнота, чтение, PATCH, повторное открытие,
превью списка и два конкурентных PATCH с ответами 200 и 409. PNG 200×200
успешно загружен как аватар и прочитан анонимно по публичному URL SeaweedFS.
После проверки временный Compose-проект и его volumes удалены.

Проверена команда переноса с реальным PostgreSQL и S3 HTTP-клиентом: перенос,
повтор без повторного чтения подтверждённого объекта, отдельная read-only сверка.
CI test получает PostgreSQL 18 и TEST_POSTGRES_DSN, поэтому обычные SQL-тесты
не пропускаются; только минутная проверка 128 МиБ остаётся opt-in.

После объединения с api-13 подключён настоящий порт активной сессии и проверен
совместный HTTP-сценарий с PostgreSQL и Redis. Синхронизация BFF, правка production env в
infra, перенос реальных S3-данных и проверка карточек с фронтендером на стенде
и production остаются отдельными интеграционными действиями. Реальные данные
и production этой проверкой не изменялись.
