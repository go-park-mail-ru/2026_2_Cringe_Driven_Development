# Редактирование ipynb

Пользователь определяется по `Authorization: Bearer <access_token>`.
Все запросы требуют `X-BFF-Key`, как у остальных операций API.
Запросы отправляет BFF; cookie и CSRF обрабатывает клиентская сторона BFF,
Go API их не использует. Префикс маршрутов — `/api/v1`.

| Метод и путь | Запрос | Ответ |
| --- | --- | --- |
| `GET /notebooks/{id}/content` | — | `200 {hash, cells}` |
| `POST /notebooks/{id}/content/cells` | `{kind, source, index?}` | `201 {hash, cell}` |
| `PATCH /notebooks/{id}/content/cells/{cell_id}` | `{source}` | `200 {hash, cell}` |
| `POST /notebooks/{id}/content/cells/{cell_id}/move` | `{index}` | `200 {hash}` |
| `DELETE /notebooks/{id}/content/cells/{cell_id}` | — | `200 {hash}` |

Изменяющие запросы передают `If-Match` с последним хешем в двойных кавычках:
`If-Match: "<hash>"`. Успешный ответ возвращает хеш в JSON и тот же хеш в кавычках
в `ETag`. Хеш непрозрачен для клиента; вычислять или интерпретировать его не нужно.
Списки ETag, wildcard, слабые ETag и повторяющиеся заголовки не принимаются (`400`).

`kind` — `code` или `markdown`; редактирование меняет полный `source`, включая
пустую строку, сохраняя тип и ID. Индексы начинаются с нуля. Без `index` новый блок
добавляется в конец; при перемещении индекс означает итоговую позицию блока.
Остальные блоки сохраняют относительный порядок. Последний блок можно удалить.
Максимум — 1000 блоков, превышение даёт `409 too_many_cells`.

Если две сессии прочитали один хеш, первая запись изменяет редакцию; вторая
получает `409 notebook_conflict`, её операция не применяется. Клиент повторяет
GET content и сверяет актуальные блоки со своими несохранёнными изменениями.
Простая замена хеша в старом запросе без сверки может перезаписать чужую правку.
После ошибки сети или `500` также следует перечитать содержимое перед повтором.
Неизменяющая операция сохраняет прежний хеш и время изменения.

Ручки `POST /notebooks/{id}/cells` и `DELETE /notebooks/{id}/cells/{index}`
также требуют `If-Match` с хешем из `GET /notebooks/{id}/content`.
Проверка хеша выполняется до выбора блока по индексу: запрос из устаревшей
вкладки получает `409 notebook_conflict` и не меняет блокнот. После успешной
операции перечитайте содержимое для получения нового хеша.

## Ограничения размеров

Максимальный `source` одного блока — 64 КиБ в UTF-8, HTTP-тело — 512 КиБ,
полный сериализованный ipynb — 128 МиБ, включая metadata, attachments и outputs.
Превышение возвращает `413 validation_error`; новая редакция не публикуется.
Ограничения проверяются при чтении запроса, в сценарии изменения и при чтении
и записи S3. Потоки без `Content-Length` также ограничены.

## Хранение

Хеш — SHA-256 точных байтов ipynb. Под блокировкой строки PostgreSQL сервер
сравнивает хеш и применяет операцию. Новый ipynb загружается под новым уникальным
S3-ключом; затем одной транзакцией обновляются `file_key`, `cells_count` и
`updated_at`. До успешной публикации старая редакция остаётся доступной.
При ошибке коммита текущую ссылку следует перечитать: результат COMMIT может быть
неопределённым для клиента. Нельзя удалять новый объект только по ошибке COMMIT.

Старые и не опубликованные объекты сохраняются. Их очистка и политика хранения
версий требуют отдельной задачи; при активном редактировании объём S3 растёт.
S3 versioning можно включить на бакете, но корректность не зависит от этой настройки.
SQL-миграции для этого механизма не нужны.

Редактирование сохраняет metadata блокнота и блоков, attachments и дополнительные
поля ipynb. Изменение `source` блока code сбрасывает только его `outputs` и
`execution_count`; перемещение сохраняет результаты исполнения.
