## Общие правила типов и целостности

- Все SQL ID — положительные integer с `GENERATED ALWAYS AS IDENTITY`, явными
  NOT NULL и PRIMARY KEY. FK также integer. Все строки — text.
- Все поля обязательны, кроме явно перечисленных в описаниях отношений.
- Значения по умолчанию: ID выдаёт identity; created_at/updated_at —
  CURRENT_TIMESTAMP; start_time у runtime_session и user_subscription —
  CURRENT_TIMESTAMP. Начало исполнения фиксируется при фактическом старте кода,
  не при постановке в очередь; если транзакция началась раньше, worker передаёт
  фактическое время явно.
- У остальных обязательных полей defaults отсутствуют: логин, хеш, ссылки,
  имена, файлы, условия тарифа, окончание подписки и срок промокода должны быть
  заданы осознанно.
  У необязательных полей нет явного DEFAULT: пропуск даёт NULL, а не пустую строку.
- Все даты событий — timestamptz, конечные; updated_at не раньше created_at.
  ID и created_at неизменяемы; общий триггер устанавливает updated_at при UPDATE.
- runtime_limit и duration — секунды; ram_limit — MiB; cpu_limit — ядра.
  Суточное время сравнивается с лимитом без округления каждого запуска до целых секунд.
  price_rub — numeric(12,2), чтобы хранить рубли и копейки без ошибок floating point.
- Все FK имеют ON UPDATE RESTRICT. ON DELETE описан для каждого отношения.
- В SQL нет JSON/JSONB, массивов, составных или диапазонных столбцов, serial,
  varchar и ORM. Выражение диапазона в EXCLUDE не является хранимым атрибутом.
- Поиск, код Python/R, текст, результаты исполнения и комментарии находятся
  внутри стандартного ipynb в S3; PostgreSQL хранит только описанные отношения.

## Доказательство нормализации

Ниже приведено покрытие функциональных зависимостей (ФЗ) каждого отношения:
для каждого кандидатного ключа перечислены все остальные атрибуты.
Тривиальные ФЗ, зависимости от суперключей и следствия аксиом Армстронга
подразумеваются. Условные уникальности отдельно оговорены и не объявляются
кандидатными ключами всего отношения. Блоки с ФЗ — `text`, не Mermaid.

Для каждого SQL-отношения применимо следующее доказательство:

1. **1НФ:** каждый атрибут имеет одно скалярное значение; повторяющихся групп нет.
2. **2НФ:** неключевые атрибуты зависят от каждого кандидатного ключа целиком;
   зависимости от собственных частей составных ключей отсутствуют.
3. **3НФ:** нет транзитивных зависимостей неключевых атрибутов от ключей через
   неключевые определители. Данные связанных сущностей хранятся отдельно.
4. **НФБК:** определитель каждой нетривиальной ФЗ модели — суперключ.
   Проверяются все кандидатные ключи, не только искусственный id.

Предметные основания для этих утверждений приведены под каждым отношением.
CHECK, частичные UNIQUE и проверки между отношениями описывают допустимые
состояния, но не заменяют анализ ФЗ. Нормализация таблиц PostgreSQL не объявляется
доказательством НФБК вложенного JSON-содержимого ipynb.

## Эволюция отношений от 1НФ до НФБК

Раздел показывает, как из исходных данных получены итоговые таблицы. Имена
атрибутов на промежуточных шагах описательные; суррогатные `id`, `created_at`
и `updated_at` добавлены на последнем шаге и здесь опущены.

### Исходные данные: не 1НФ

Если записать предметную область «как есть», получаются две записи с
повторяющимися группами:

```text
проект(название, владелец {логин, хеш пароля, аватар {ключ S3, расширение}},
       блокнот {ключ S3, расширение},
       файлы окружения [{путь в проекте, ключ S3, расширение}],
       доступы [{логин получателя}],
       запуски [{начало, конец}])

пользователь(логин, хеш пароля,
             подписки [{начало, конец, тариф {название, лимиты, цена, срок}}],
             платежи [{время, тариф {...}, промокод {код, срок действия}}])
```

Списки в квадратных скобках — не скалярные значения, поэтому это не 1НФ.

### Шаг 1: 1НФ

Каждая повторяющаяся группа становится отдельным отношением: одна строка — один
элемент списка. Вложенные записи раскрыты в обычные столбцы. Ключ отношения —
левая часть зависимости, записанной под ним.

```text
project_file_1(project, path, s3_key, extension,
               project_name, owner_login, owner_hash,
               notebook_key, notebook_extension)
{project, path} -> все остальные атрибуты

project_share_1(project, recipient_login, recipient_hash,
                recipient_avatar_key, recipient_avatar_extension,
                project_name, owner_login)
{project, recipient_login} -> все остальные атрибуты

project_run_1(run, project, start_time, end_time, project_name, owner_login)
{run} -> все остальные атрибуты

subscription_1(user_login, start_time, end_time, user_hash,
               type_name, runtime_limit, ram_limit, cpu_limit, price_rub, duration)
{user_login, start_time} -> все остальные атрибуты

payment_1(payment, user_login, user_hash,
          type_name, runtime_limit, ram_limit, cpu_limit, price_rub, duration,
          promo_code, promo_expires_at)
{payment} -> все остальные атрибуты
```

У запуска и платежа нет естественного ключа: два платежа одного пользователя
за один тариф различимы только номером. Поэтому номер введён уже здесь.

Все значения скалярны: 1НФ выполнена. Данные проекта, пользователя и тарифа
повторяются в каждой строке — отсюда аномалии: переименование проекта требует
правки многих строк, проект без файлов и доступов негде записать.

### Шаг 2: 2НФ

Убираются зависимости от части составного ключа:

```text
project_file_1:   {project} -> project_name, owner_login, owner_hash,
                               notebook_key, notebook_extension
project_share_1:  {project} -> project_name, owner_login
                  {recipient_login} -> recipient_hash, recipient_avatar_key,
                                       recipient_avatar_extension
subscription_1:   {user_login} -> user_hash
```

Правые части выносятся в отношения с ключом-определителем:

```text
project_2(project, project_name, owner_login, owner_hash,
          notebook_key, notebook_extension)
user_2(login, hash, avatar_key, avatar_extension)

environment_file_2(project, path, s3_key, extension)
project_share_2(project, recipient_login)
subscription_2(user_login, start_time, end_time,
               type_name, runtime_limit, ram_limit, cpu_limit, price_rub, duration)
```

`project_run_1` и `payment_1` имеют простой ключ, частичных зависимостей в них
быть не может; они уже во 2НФ.

### Шаг 3: 3НФ

Убираются зависимости неключевых атрибутов от других неключевых:

```text
project_2:           owner_login -> owner_hash
                     notebook_key -> notebook_extension
user_2:              avatar_key -> avatar_extension
environment_file_2:  s3_key -> extension
project_run_1:       project -> project_name, owner_login
subscription_2:      type_name -> runtime_limit, ram_limit, cpu_limit, price_rub, duration
payment_1:           user_login -> user_hash
                     type_name -> runtime_limit, ram_limit, cpu_limit, price_rub, duration
                     promo_code -> promo_expires_at
```

Каждая такая зависимость описывает самостоятельную сущность. Получаются:

```text
file(s3_key, extension)                       -- блокнот, аватар, файл окружения
app_user(login, hash, avatar_key)
project(project, name, owner_login, notebook_key)
environment_file(project, path, s3_key)
project_share(project, recipient_login)
runtime_session(run, project, start_time, end_time)
subscription_type(name, runtime_limit, ram_limit, cpu_limit, price_rub, duration)
user_subscription(user_login, start_time, end_time, type_name)
promo_code(code, expires_at)
payment(payment, user_login, type_name, promo_code)
```

Сумма платежа не хранится. Она выводится из тарифа и промокода:
`{type_name, promo_code} -> amount`, то есть зависела бы от неключевых атрибутов.
Промокод полностью покрывает цену, иначе сумма равна `price_rub`; условия
использованного тарифа неизменяемы, поэтому значение не теряется.
По той же причине не хранятся длительность запуска и признак бесплатного тарифа.

### Шаг 4: НФБК

Проверяются все определители, включая альтернативные ключи:

- `project`: блокнот принадлежит ровно одному проекту, поэтому `notebook_key` —
  тоже ключ. Определитель является суперключом, нарушения нет.
- `environment_file`: объект S3 входит ровно в один проект, поэтому `s3_key` —
  второй ключ наряду с `{project, path}`.
- `user_subscription`: интервалы пользователя не пересекаются, поэтому
  `{user_login, end_time}` — второй ключ наряду с `{user_login, start_time}`.
- В остальных отношениях определитель единственный, и это ключ.

Нетривиальных ФЗ с определителем, не являющимся суперключом, не осталось:
все десять отношений находятся в НФБК.

### Шаг 5: суррогатные ключи

Естественные ключи заменены в ссылках на целочисленные `id`: логин и название
тарифа можно изменить, не трогая ссылающиеся строки, а ключ S3 и путь не
копируются в другие таблицы. Естественные ключи остались как UNIQUE и перечислены
в ФЗ каждого отношения ниже. Во все отношения добавлены `created_at` и
`updated_at`, зависящие только от ключа.

| Итоговая таблица | Шаг, на котором выделена | Причина |
|---|---|---|
| environment_file, project_share, runtime_session, user_subscription, payment | 1НФ | Повторяющаяся группа |
| project, app_user | 2НФ | Зависимость от части ключа |
| file, subscription_type, promo_code | 3НФ | Транзитивная зависимость |

## Отношения PostgreSQL

### app_user

Учётная запись пользователя и ссылка на его необязательный аватар.

Атрибуты: `id`, `avatar_image_id`, `login`, `password_hash`, `created_at`, `updated_at`.

Функциональные зависимости:

```text
{id} -> avatar_image_id, login, password_hash, created_at, updated_at
{login} -> id, avatar_image_id, password_hash, created_at, updated_at
```

**NULL:** Только avatar_image_id; отсутствие аватара — NULL. Все остальные поля NOT NULL.

**Ограничения:** login хранится в нижнем регистре, 3–32 ASCII-символа [a-z0-9_]. UNIQUE обеспечивает вход без учёта регистра при нормализации ввода приложением. password_hash — bcrypt; проверка формата хеша не заменяет проверку пароля до хеширования. Аватар не уникален.

**Связи и удаление:** avatar_image_id → file.id: RESTRICT. Ссылки из project, user_subscription и payment блокируют удаление пользователя; его полученные project_share удаляются CASCADE.

**1НФ–НФБК:** id и login — кандидатные ключи. Аватар не определяет пользователя: один объект может использоваться несколькими пользователями. Все атрибуты скалярны; частичных и транзитивных неключевых зависимостей нет.

### project

Проект одного владельца с одним ipynb. Файлы окружения — в environment_file.

Атрибуты: `id`, `user_id`, `notebook_file_id`, `name`, `created_at`, `updated_at`.

Функциональные зависимости:

```text
{id} -> user_id, notebook_file_id, name, created_at, updated_at
{notebook_file_id} -> id, user_id, name, created_at, updated_at
```

**NULL:** Нет. Проект без файлов окружения не имеет строк в environment_file. Все остальные поля NOT NULL.

**Ограничения:** name — 1–200 символов без крайних пробелов; одинаковые имена разрешены. notebook_file_id уникален. Владелец неизменяем: для другого владельца создаётся копия.

**Связи и удаление:** user_id → app_user.id, notebook_file_id → file.id: RESTRICT. runtime_session препятствует удалению проекта с историей запусков. Доступы project_share и строки environment_file удаляются CASCADE.

**1НФ–НФБК:** id и обязательная уникальная ссылка на блокнот — кандидатные ключи. Имя и user_id могут повторяться; свойства пользователя и файла не дублируются. Все атрибуты скалярны; частичных и транзитивных неключевых зависимостей нет.

### environment_file

Один файл окружения проекта: датасет, requirements.txt и подобное. Содержимое находится в S3.

Атрибуты: `id`, `project_id`, `file_id`, `path`, `created_at`, `updated_at`.

Функциональные зависимости:

```text
{id} -> project_id, file_id, path, created_at, updated_at
{file_id} -> id, project_id, path, created_at, updated_at
{project_id, path} -> id, file_id, created_at, updated_at
```

**NULL:** Нет. Все остальные поля NOT NULL.

**Ограничения:** path — путь внутри проекта, 1–1024 символа без крайних пробелов, не начинается и не заканчивается на `/`; например `data/train.csv`. UNIQUE(project_id, path): в проекте один файл по одному пути. UNIQUE(file_id): объект S3 принадлежит одному проекту. Переименование и перемещение — UPDATE одного поля path: ключ объекта в S3 не меняется. Добавление и удаление — одна строка и один объект. Каталоги отдельно не хранятся: они следуют из путей.

**Связи и удаление:** project_id → project.id: CASCADE. file_id → file.id: RESTRICT. Запись file и объект S3 после удаления строки убирает приложение. Файл окружения не должен совпадать с блокнотом или аватаром; это межтабличное условие проверяет приложение.

**1НФ–НФБК:** id, file_id и пара project_id/path — кандидатные ключи. Проект и путь по отдельности повторяются. Расширение и ключ S3 зависят от file и сюда не копируются. Все атрибуты скалярны; частичных и транзитивных неключевых зависимостей нет.

### file

Метаданные объекта S3: ipynb, файл окружения или аватар. Содержимое находится в S3.

Атрибуты: `id`, `file_path`, `file_extension`, `created_at`, `updated_at`.

Функциональные зависимости:

```text
{id} -> file_path, file_extension, created_at, updated_at
{file_path} -> id, file_extension, created_at, updated_at
```

**NULL:** Нет. Все остальные поля NOT NULL.

**Ограничения:** file_path — уникальный непустой ключ объекта в единственном бакете пользовательских файлов, без крайних пробелов. Это не временный подписанный URL. file_extension — расширение без точки, только строчные латинские буквы и цифры; например ipynb, csv, png. Расширение не обязано быть частью ключа S3.

**Связи и удаление:** Ссылки из пользователей, проектов и файлов окружения запрещают удаление используемой записи (RESTRICT). SQL не удаляет объект S3.

**1НФ–НФБК:** id и file_path — кандидатные ключи. Расширение может повторяться и не определяет путь; свойства объекта зависят от ключа. Все атрибуты скалярны; частичных и транзитивных неключевых зависимостей нет.

### runtime_session

Один фактический запуск файла, а не время жизни контейнера. Ошибочный или отменённый запуск тоже расходует время до остановки.

Атрибуты: `id`, `project_id`, `start_time`, `end_time`, `created_at`, `updated_at`.

Функциональные зависимости:

```text
{id} -> project_id, start_time, end_time, created_at, updated_at
```

**NULL:** Только end_time: NULL означает, что запуск ещё не завершён. Все остальные поля NOT NULL.

**Ограничения:** start_time конечен; end_time конечен и не раньше start_time. Нулевая длительность допустима для немедленного завершения. Частичный UNIQUE(project_id) WHERE end_time IS NULL разрешает один незавершённый запуск в проекте. Проекты одного пользователя могут исполняться параллельно; их время суммируется.

**Связи и удаление:** project_id → project.id: RESTRICT. Владелец запуска определяется через неизменяемый project.user_id.

**1НФ–НФБК:** Глобальный кандидатный ключ — id. Проект допускает много последовательных запусков. Уникальность project_id только для незавершённых строк — условное ограничение, не глобальный ключ. Вычисляемую длительность отдельно не храним. Все атрибуты скалярны; частичных и транзитивных неключевых зависимостей нет.

### subscription_type

Тариф: суточный лимит исполнения, ОЗУ, ядра, цена в рублях и длительность покупки.

Атрибуты: `id`, `name`, `runtime_limit`, `ram_limit`, `cpu_limit`, `price_rub`, `duration`, `created_at`, `updated_at`.

Функциональные зависимости:

```text
{id} -> name, runtime_limit, ram_limit, cpu_limit, price_rub, duration, created_at, updated_at
{name} -> id, runtime_limit, ram_limit, cpu_limit, price_rub, duration, created_at, updated_at
```

**NULL:** Только duration, и только у бесплатного тарифа. Все остальные поля NOT NULL.

**Ограничения:** name уникально, 1–100 символов без крайних пробелов. runtime_limit > 0 секунд в сутки; ram_limit > 0 MiB; cpu_limit > 0 ядер. price_rub — numeric(12,2), от 0 до 9999999999.99, без NaN/Infinity. Нулевая цена обозначает бесплатный тариф: duration IS NULL; частичный UNIQUE по цене при price_rub = 0 разрешает максимум один такой тариф. У платного цена > 0 и duration > 0 секунд. Seed создаёт бесплатный тариф, триггер запрещает его удаление. Использованные условия платного тарифа и условия бесплатного неизменяемы; новый платный набор условий — новая строка с новым именем.

**Связи и удаление:** Входящие ссылки user_subscription и payment блокируют удаление использованного тарифа (RESTRICT).

**1НФ–НФБК:** id и name — кандидатные ключи. Разные платные тарифы могут иметь одинаковую цену, срок или ресурсы. Флаг is_default не храним: он однозначно выводился бы из цены и создавал бы неключевую зависимость price_rub → is_default. Все атрибуты скалярны; частичных и транзитивных неключевых зависимостей нет.

### user_subscription

Один интервал доступа пользователя к платному тарифу. Разделённая покупка Pro представлена двумя строками с тем же тарифом.

Атрибуты: `id`, `user_id`, `subscription_type_id`, `start_time`, `end_time`, `created_at`, `updated_at`.

Функциональные зависимости:

```text
{id} -> user_id, subscription_type_id, start_time, end_time, created_at, updated_at
{user_id, start_time} -> id, subscription_type_id, end_time, created_at, updated_at
{user_id, end_time} -> id, subscription_type_id, start_time, created_at, updated_at
```

**NULL:** Нет. Все остальные поля NOT NULL.

**Ограничения:** end_time > start_time; обе границы конечны. Интервалы одного пользователя не пересекаются: EXCLUDE по user_id и tstzrange(start_time, end_time, '[)'). Соседние интервалы допустимы. UNIQUE(user_id, start_time) и UNIQUE(user_id, end_time) явно фиксируют альтернативные ключи, следующие из непересечения. Ограничения отложены до COMMIT для изменения таймлайна одной транзакцией. Бесплатный тариф сюда не записывается; это проверяет межтабличный триггер.

**Связи и удаление:** user_id → app_user.id и subscription_type_id → subscription_type.id: RESTRICT. Исторические интервалы сохраняются.

**1НФ–НФБК:** id, пара user_id/start_time и пара user_id/end_time — кандидатные ключи. Ни пользователь, ни отдельная дата не определяют остальные поля. Срок интервала может быть короче duration тарифа после замещения; тариф не определяет границы интервала. Все атрибуты скалярны; частичных и транзитивных неключевых зависимостей нет.

### promo_code

Промокод, который засчитывается как полная оплата любого платного тарифа.

Атрибуты: `id`, `code`, `expires_at`, `created_at`, `updated_at`.

Функциональные зависимости:

```text
{id} -> code, expires_at, created_at, updated_at
{code} -> id, expires_at, created_at, updated_at
```

**NULL:** Нет. Все остальные поля NOT NULL.

**Ограничения:** code уникален, 4–32 символа [A-Z0-9]; приложение приводит ввод к верхнему регистру. expires_at конечен и позже created_at. Промокод не привязан к тарифу и не хранит скидку: он покрывает цену целиком.

**Связи и удаление:** Входящие ссылки payment блокируют удаление использованного промокода (RESTRICT).

**1НФ–НФБК:** id и code — кандидатные ключи. Срок действия может совпадать у разных промокодов и ничего не определяет. Все атрибуты скалярны; частичных и транзитивных неключевых зависимостей нет.

### payment

Подтверждённая оплата тарифа пользователем: промокодом или через платёжный сервис.

Атрибуты: `id`, `user_id`, `subscription_type_id`, `promo_code_id`, `created_at`, `updated_at`.

Функциональные зависимости:

```text
{id} -> user_id, subscription_type_id, promo_code_id, created_at, updated_at
```

**NULL:** Только promo_code_id: NULL означает оплату через платёжный сервис. Все остальные поля NOT NULL.

**Ограничения:** UNIQUE(user_id, promo_code_id): один промокод засчитывается пользователю один раз; на строки без промокода ограничение не действует. Триггер check_payment запрещает платёж за бесплатный тариф и использование промокода с истёкшим сроком. Пользователь, тариф и промокод платежа неизменяемы (триггер protect_payment). Сумма не хранится: при оплате промокодом она равна нулю, иначе — price_rub тарифа, условия которого после первого использования неизменяемы.

**Связи и удаление:** user_id → app_user.id, subscription_type_id → subscription_type.id, promo_code_id → promo_code.id: RESTRICT. История платежей сохраняется.

**1НФ–НФБК:** Глобальный кандидатный ключ — id. Пользователь может оплатить один тариф много раз, поэтому пара пользователь/тариф не ключ. Уникальность пары user_id/promo_code_id действует только для строк с промокодом — условное ограничение, не ключ всего отношения. Промокод не определяет тариф, тариф не определяет промокод. Все атрибуты скалярны; частичных и транзитивных неключевых зависимостей нет.

Платёж и интервал user_subscription создаются приложением в одной транзакции. Внешнего ключа между ними нет: интервал позже может быть разделён покупкой другого тарифа, а ссылка на платёж в каждой части дублировала бы пользователя и тариф (payment_id → user_id, subscription_type_id).

### project_share

Адресный доступ зарегистрированного пользователя к просмотру и комментированию проекта.

Атрибуты: `id`, `project_id`, `user_id`, `created_at`, `updated_at`.

Функциональные зависимости:

```text
{id} -> project_id, user_id, created_at, updated_at
{project_id, user_id} -> id, created_at, updated_at
```

**NULL:** Нет. Все остальные поля NOT NULL.

**Ограничения:** UNIQUE(project_id, user_id): один доступ на пару. Ролей редактора или исполнителя нет. Доступ самому владельцу запрещён триггером check_project_share: владелец записан в project, и обычный CHECK одной строки его не видит. Выдать и отозвать доступ может только владелец; эту проверку полномочий выполняет приложение.

**Связи и удаление:** project_id → project.id и user_id → app_user.id: CASCADE. Удаление доступа не удаляет пользователя, проект или комментарии.

**1НФ–НФБК:** id и пара project_id/user_id — кандидатные ключи. Каждый компонент пары повторяется; только вся пара определяет доступ и даты. Владелец проекта сюда не копируется: столбец владельца ради декларативного CHECK дал бы зависимость project_id → owner_id от части ключа и нарушил бы 2НФ. Все атрибуты скалярны; частичных и транзитивных неключевых зависимостей нет.

## Redis: refresh_session

Логическая сессия авторизации, физически Redis Hash. Все значения обязательны.

| Атрибут | Правило |
|---|---|
| id | Положительный integer, логический PK; выдаётся атомарным INCR общего счётчика |
| user_id | Положительный integer пользователя app_user |
| token_hash | Уникальный SHA-256 refresh-токена: 64 строчных hex-символа |
| expires_at | Время истечения UTC, строго позже created_at |
| created_at | Время выпуска UTC, по умолчанию текущее время сервиса |

```text
{id} -> user_id, token_hash, expires_at, created_at
{token_hash} -> id, user_id, expires_at, created_at
```

В логическом представлении id и token_hash — кандидатные ключи; значения
скалярны, частичных и транзитивных неключевых ФЗ нет: 1НФ–НФБК соблюдены.
Redis физически кодирует integer и даты строками, но сервис проверяет их домены.
Ключ `refresh:<token_hash>` содержит Hash с id, user_id, expires_at, created_at.
Счётчик `refresh_session:id` не имеет TTL, не сбрасывается и не переиспользует ID;
при выходе за предел положительного integer создание сессии отклоняется.
Токен генерирует сервис; пользователь, хеш и expires_at не имеют defaults.

TTL соответствует expires_at. Сессия неизменяема; при ротации создаётся новая,
поэтому updated_at отсутствует обоснованно. Проверка старой сессии, её удаление
и создание новой выполняются атомарно в Redis. Пароли и исходные токены не хранятся.
Нет SQL FOREIGN KEY на app_user и общей транзакции PostgreSQL/Redis: существование
пользователя проверяет сервис. Удаление пользователя сопровождается отзывом его
сессий; без существующего пользователя оставшийся ключ не даёт доступа.

Redis Pub/Sub для комментариев хранит только временные события доставки.
Канал `project:<id>:comments` сообщает участникам об изменении файла.
Это не таблица и не история сообщений; после переподключения клиент перечитывает ipynb.

## S3: ipynb, файлы окружения и аватары

В одном бакете пользовательских файлов хранятся:

- ipynb: блоки Python/R и Markdown, metadata, результаты исполнения;
- файлы окружения проекта: каждый файл — отдельный объект;
- изображения аватаров.

`file.file_path` — ключ объекта в этом бакете; bucket задаётся конфигурацией сервиса.
Метаданные file находятся в PostgreSQL, содержимое — в S3. Между ними нет SQL FK.
Загрузка и проверка содержимого, соответствие расширения назначению, отсутствие
ссылок перед удалением объекта, обработка ошибок S3 — обязанности приложения.
Seed не создаёт фиктивные объекты или ссылки на отсутствующие файлы.

Формат ipynb допускает пользовательские metadata. Комментарии сохраняются
в `cell.metadata.colab_cdd.comments`, как предложил backend-ментор:

| Поле комментария | Правило |
|---|---|
| id | Положительный integer, уникальный в проекте, не переиспользуется |
| author_id | Integer пользователя; назначает сервис по авторизованной сессии |
| body | Text, 1–10000 символов после удаления крайних пробелов |
| created_at, updated_at | UTC RFC3339; обе даты обязательны; обновление не раньше создания |

Следующий номер — `notebook.metadata.colab_cdd.next_comment_id`; сервер увеличивает
его при записи комментария. Логический ключ комментария — `{project_id, id}`:
он определяет блок, автора, текст и даты. Это вложенный объект файла, не SQL-отношение.
Собственные ID комментариев целочисленные; стандартный `cell.id` nbformat — строка
1–64 символа `[A-Za-z0-9_-]`, уникальная внутри блокнота, а не SQL ID.

Владелец редактирует файл и удаляет любые комментарии. Получатель шеринга читает
проект, создаёт комментарии, редактирует/удаляет собственные; менять код и запускать
его нельзя. При удалении блока удаляются его вложенные комментарии. Импорт чужого
ipynb очищает служебные комментарии, чтобы не подделывать авторство.
Физическое удаление пользователя с авторством в файлах требует обработки внешних
ссылок приложением; PostgreSQL эти ссылки не проверяет.

Изменения ipynb сериализуются приложением по проекту: взять блокировку строки
project, проверить доступ, прочитать актуальный файл, применить только разрешённую
операцию и сохранить. Отзыв доступа использует ту же блокировку. Событие WebSocket
через Redis публикуется после успешного сохранения. S3 и PostgreSQL не имеют общей
транзакции: ошибки сохранения и повтор операции обрабатывает приложение.

Копирование создаёт новый project владельца копии и новые file/S3-объекты для
ipynb и каждого файла окружения. Код, текст и outputs копируются; комментарии и
доступы не переносятся. Проектам запрещено совместно использовать один ipynb или
файл окружения, чтобы изменение копии не меняло оригинал. Поиск читает source блоков; экспорт после исполнения
возвращает ipynb с outputs. ИИ-чат в эту модель не входит.

Источник: [формат ipynb и пользовательские metadata](https://nbformat.readthedocs.io/en/stable/format_description.html#metadata).
Файлы окружения хранятся по отдельности, а не одним архивом: переименование,
перемещение, добавление и удаление файла меняют одну строку environment_file
и не требуют пересборки архива и синхронизации его содержимого с БД. Окружение
для запуска собирает сервис исполнения: читает строки проекта и раскладывает
объекты S3 по их path.

По решению команды JSON существует только внутри стандартного файла в S3;
SQL-столбцов JSON/array/composite нет. Это явно указанная граница модели для ревью СУБД.

## Подписки: таймлайн без продления первоначального срока

При отсутствии текущего платного интервала применяется единственный тариф
с price_rub = 0. Ежедневные бесплатные user_subscription не создаются.
Интервал платной подписки полуоткрытый: start_time <= момент < end_time.

При покупке в момент T нового тарифа длительностью D приложение в одной
транзакции под блокировкой app_user:

1. Создаёт строку payment и фиксирует новый интервал `[T, T + D)`. При оплате
   промокодом в payment записывается promo_code_id; иначе оплату подтверждает
   платёжный сервис, и ссылка остаётся NULL.
2. Для каждого пересекаемого прежнего интервала сохраняет только непустые части
   до T и после T + D. Если интервал уже закончился, он остаётся без изменений.
3. Продолжение прежнего тарифа заканчивается в его **первоначальный end_time**.
   Новая покупка не сдвигает эту дату. Если дата уже прошла к окончанию нового тарифа,
   продолжение не создаётся. Интервал нулевой длины не вставляется.
4. COMMIT проверяет EXCLUDE и UNIQUE. При конфликте конкурентных покупок
   транзакция откатывается; приложение повторно читает таймлайн.

Пример: Pro `[0, 30)` суток; Max покупается в день 10 на 7 суток.
Результат: Pro `[0, 10)`, Max `[10, 17)`, Pro `[17, 30)` — не до дня 37.
Если Max куплена в день 28 на неделю, остаются Pro `[0, 28)` и Max `[28, 35)`;
продолжения Pro нет. Условие `end_time - start_time = duration` не вводится:
после переключения сохранённый интервал имеет меньшую длительность.

## Суточная квота и история запусков

runtime_session начинается только при фактическом исполнении файла.
Время очереди, подготовки машины и простоя контейнера не входит в интервал.
end_time записывается после подтверждённой остановки, включая ошибку или отмену.
Продолжительность — elapsed time выполнения кода, а не CPU-время процесса.
Пауза между независимыми запусками не тарифицируется. В одном проекте допускается
один незавершённый запуск; в разных проектах — несколько.

Сутки определяются в UTC, интервалом `[B, E)` между двумя полуночами.
Для запуска его вклад в секунды равен:

```text
max(0, min(coalesce(end_time, now), E) - max(start_time, B))
```

Здесь разность дат переводится в секунды. Сумма по всем проектам пользователя —
его суточный расход. Незавершённые запуски учитываются до текущего момента;
после полуночи их часть до B относится к предыдущим суткам. Отдельной таблицы
расхода и сохраняемого вычисляемого runtime_time нет. Дробные секунды не отбрасываются.

Лимит задаёт текущий тариф. После 20 минут на Pro при переходе на Max с лимитом
120 минут остаётся 100 минут. Расход не сбрасывается при покупке или возврате
на Pro. Если расход выше лимита текущего тарифа, новые запуски запрещены до
следующих суток либо смены тарифа. Неиспользованное время не переносится.

Суммирование параллельных запусков, проверка лимита перед стартом, остановка
worker при исчерпании и обработка пропавшего worker относятся к приложению.
Старт и изменение подписок сериализуются блокировкой пользователя. При смене
тарифа приложение завершает старые исполнения, фиксирует их end_time и применяет
новую конфигурацию. PostgreSQL не останавливает контейнеры по часам; до подтверждения
остановки незакрытая строка продолжает учитываться в расходе.

Сохраняемые runtime_session дают историю запусков: когда исполнялся проект
и сколько времени потрачено, в том числе по дням. user_subscription сохраняет
историю предоставленного доступа к тарифам. Завершённые запуски приложение
не переписывает и не удаляет; исторические интервалы подписок не очищает.
Проекты с запусками и пользователи с подписками защищены входящими FK от удаления.
Обход правил владельцем БД не является моделью пользовательского доступа.

Из переписки с backend-ментором от 29.09.2026: дополнительно нужны структурированные
логи действий через slog в stdout и передача request-id между сервисами.
Это рекомендация для реализации приложения, а не часть данных таблиц и не
заявление о готовом аудите. created_at/updated_at не восстанавливают прежние значения.
На ревью СУБД предложены конкретные сущности истории: запуски и интервалы подписок;
аппрув преподавателя не подменяется ответом backend-ментора. Дополнительные системы
логирования и таблицы версий в ДЗ не добавляются.

## Обоснование триггеров и границы проверок

- touch_row обновляет updated_at, защищает id/created_at и неизменность владельца
  проекта, от которого зависит расчёт его исторического расхода.
- check_subscription_type запрещает строку покупки бесплатного тарифа. FOR SHARE
  блокирует одновременное изменение условий тарифа при оформлении подписки.
- protect_subscription_type защищает уже использованные экономические условия
  от изменения задним числом; бесплатный тариф фиксирован и не удаляется.
  Название тарифа можно исправить. Неиспользованный платный тариф можно изменить.
- check_payment запрещает платёж за бесплатный тариф и просроченный промокод;
  protect_payment делает пользователя, тариф и промокод платежа неизменяемыми.
- check_project_share запрещает выдать доступ владельцу проекта. Владелец
  неизменяем, поэтому проверки со стороны project не требуется.

Эти правила требуют проверки старой строки или связанной таблицы, поэтому не
выражаются обычным CHECK. Непересечение интервалов проверяет декларативный EXCLUDE
с расширением btree_gist. Триггерного планировщика и отдельной таблицы периодов нет.
Частичный UNIQUE бесплатного тарифа задаёт максимум одну строку; её наличие
обеспечивает seed, а сохранность — триггер. ФЗ и НФБК описываются для итогового
согласованного состояния транзакции.

Проверки полномочий, пароля до хеширования, фактического содержимого файлов,
подтверждения оплаты платёжным сервисом и остановки исполнения выполняет приложение.
Между S3/Redis и PostgreSQL нет физических FK и ON DELETE CASCADE.

| Исполнение и вывод | runtime_session и outputs в ipynb |
| Шеринг и копирование | project_share, самостоятельный проект и файлы копии |
| Комментарии, WebSocket | metadata ipynb, Redis Pub/Sub для уведомлений |
| Файлы окружения | environment_file, объекты в S3 |
| Импорт и экспорт после исполнения | ipynb в S3 |
| Подписки и конфигурация машины | subscription_type, user_subscription |
| Оплата и промокоды | payment, promo_code |
| Квота и статистика времени | интервалы runtime_session, сумма за сутки UTC |
| История | сохранённые запуски и интервалы подписок |

По уточнению команды лимитируется только время исполнения; лимита количества
запусков нет. CPU/RAM — конфигурация тарифа, а не дополнительные единицы списания.
Показ текущей нагрузки при необходимости получает значения от worker;
историческая телеметрия CPU/RAM отдельными таблицами не проектируется.

## SQL-миграции и проверка

Миграции написаны на SQL с разделами Goose Up/Down:

1. `202609290001_schema.sql` — десять отношений, ключи, CHECK, EXCLUDE и индексы.
2. `202609290002_integrity.sql` — перечисленные служебные и межтабличные триггеры.
3. `202609290003_seed.sql` — alice/bob, Free/Pro/Max, пример таймлайна, промокод и платежи.

Применение — по номеру, откат — в обратном порядке, каждая миграция транзакционна.
Для отдельной пустой PostgreSQL 18 БД с правом создания btree_gist и установленным Goose:

```bash
goose -dir db/migrations postgres "$DB_DSN" up
goose -dir db/migrations postgres "$DB_DSN" down
```

`DB_DSN` указывает на учебную БД, не на БД работающего API. Команда down откатывает
одну миграцию. При полном откате схема colab удаляется; btree_gist оставляется,
чтобы не удалить расширение, используемое другими схемами.

У alice и bob учебный пароль `DemoPass123!`; в SQL хранится только bcrypt-хеш.
Числа тарифов демонстрационные. Bob использует Free без строки подписки.
Учебный промокод — `DEMO2026`; alice оплатила им Max, а Pro — без промокода.
В примере месяц равен фиксированным 30 суткам; календарные месяцы не моделируются.

Драйвер существующего проекта — pgx/v5; приложение и его прежние миграции
в этом ДЗ не переводятся на новую модель. Схема colab не подключается к API
автоматически. Реализация обработчиков, worker, WebSocket и интеграции с платёжным
сервисом здесь не выполняется.
